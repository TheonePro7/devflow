## 1. using-superpowers

### 全名
`using-superpowers`

### 描述
"在任何对话开始时使用——确立如何查找和使用技能，要求在做出任何回应（包括澄清性问题）之前必须先调用 Skill 工具"

### 完整流程步骤
1. 收到用户消息
2. 检查是否有任何技能可能适用（哪怕只有 1% 的可能）
3. 如果是 -> 调用 Skill 工具 -> 声明"使用 [技能] 来 [目的]" -> 严格遵循技能内容
4. 如果技能有检查清单 -> 为每个项目创建 TodoWrite
5. 如果没有技能适用 -> 做出回应（包括澄清）
6. 如果即将进入 EnterPlanMode -> 检查是否已完成头脑风暴 -> 如果未完成，则调用 brainstorming

### HARD GATE 注解
- **`<EXTREMELY-IMPORTANT>`**：如果你认为哪怕只有 1% 的可能一个技能适用，你**绝对必须**调用该技能。如果一个技能适用于你的任务，你没有选择。你必须使用它。这是不可协商的。
- **`<SUBAGENT-STOP>`**：如果你是作为子代理被派去执行特定任务的，跳过此技能。
- 技能检查先于澄清性问题——此顺序被强制执行。
- 技能检查先于代码库探索。
- 声明格式为："我正在使用 using-git-worktrees 技能来设置一个隔离的工作空间"。
- 技能覆盖默认的系统提示，但用户指令（CLAUDE.md、GEMINI.md、AGENTS.md、直接请求）拥有最高优先级。

### 输入/输出预期
- **输入：** 任何用户请求或任务
- **输出：** 调用并遵循了适当的技能，或确定了结构化的方法

### 与其他技能的集成
- **所有技能的入口点**——路由调度到所有其他技能
- 如果尚未进行头脑风暴且即将进行创意工作，则调用 brainstorming
- 提供平台适配：Skill 工具（Claude Code）、skill 工具（Copilot CLI）、activate_skill（Gemini CLI）

### 工具注入点
- Skill 工具（主要）
- TodoWrite（用于检查清单追踪）
- Read（绝不用于读取技能文件——改用 Skill 工具）

### 核心精神
**技能是强制性的，而非可选的。**"1% 概率"规则意味着误报的成本（浪费一点时间阅读无关的技能内容）远远低于漏报的成本（错过一个能防止浪费工作的技能）。12 行的合理化预防表明确针对每一种可能的跳过技能检查的借口。这个技能是整个 superpowers 系统的守门人——没有它，其他任何技能都不会被调用。

## 2. brainstorming

### 全名
`brainstorming`

### 描述
"你必须在任何创意工作之前使用它——创建功能、构建组件、添加功能或修改行为。在实现之前探索用户意图、需求和设计。"

### 完整流程步骤
1. **探索项目上下文** —— 检查文件、文档、最近的提交
2. **提供可视化伴侣**（如果预计会有可视化问题）—— 必须作为单独的消息，不含其他内容。仅提供同意询问。如果被拒绝，则仅用文本继续。
3. **提出澄清性问题** —— 一次一个，理解目的/约束/成功标准。在提问之前，评估范围：如果请求描述了多个独立的子系统，立即标记并先进行分解。每个子项目各自经历 spec -> plan -> implementation 循环。
4. **提出 2-3 种方案** —— 附带权衡和你的推荐
5. **呈现设计** —— 分章节，按复杂度缩放。每节后询问。覆盖：架构、组件、数据流、错误处理、测试。
6. **编写设计文档** —— 保存到 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 并提交
7. **规范自审** —— 占位符扫描（TBD/TODO）、内部一致性（矛盾之处）、范围检查（是否足够聚焦于单一计划？）、歧义检查（是否有两种理解方式？）。当场修复。
8. **用户评审已编写的规范** —— "规范已编写并提交到 <路径>。请审阅，如果您想做任何修改，请告诉我，然后我们再开始编写实现计划。"等待回应。如有修改，修复后重新运行规范评审循环。
9. **过渡到实现** —— 调用 writing-plans 技能。不要调用其他任何技能。

### HARD GATE 注解
- **`<HARD-GATE>`**：在你呈现设计并获得用户批准之前，不得调用任何实现技能、不得编写任何代码、不得搭建任何项目、不得采取任何实现行动。适用于每个项目，无论你认为它多么简单。
- **反模式章节**："这事儿太简单了，不需要设计"——即使是待办列表、单函数工具或配置变更也必须经过此流程。"简单"项目恰恰是未经检验的假设造成最多浪费工作的地方。
- **终端状态强制执行**：brainstorming 之后唯一能调用的技能是 writing-plans。不能调用 frontend-design、mcp-builder 或任何其他实现技能。
- 每条消息只能问一个问题。

### 输入/输出预期
- **输入：** 用户模糊的想法或功能请求；项目上下文（文件、文档、提交记录）
- **输出：** 验证过的设计文档，位于 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`；过渡到 writing-plans

### 与其他技能的集成
- **调用：** `writing-plans`（强制下一步）
- **可能使用：** `elements-of-style:writing-clearly-and-concisely`（如果可用）
- **被调用者：** `using-superpowers`（自动路由）
- **创建工作树用于：** 专门的实现工作树（由 writing-plans 引用）
- **邀请的技能：** writing-plans（终端状态）

### 工具注入点
- Skill 工具（调用 writing-plans）
- 可视化伴侣工具（基于浏览器的原型/图表）
- Git 用于提交设计文档
- Read 用于项目上下文探索
- Write 用于设计文档文件
- TodoWrite 用于检查清单追踪

### 核心精神
**设计优先，代码其次。没有例外。**通过强制在实现之前结构化地探索用户意图来防止浪费工作。可视化伴侣的提议被刻意隔离为单独的消息（不与问题混合），以便给用户一个清晰的选择。"过大"的项目先分解为子项目，然后每个子项目经历完整循环。设计原则强调小而专注的单元，带有定义良好的接口——这与 writing-plans 中的文件结构指导和 subagent-driven-development 中的任务隔离是相同的理念。

## 3. writing-plans

### 全名
`writing-plans`

### 描述
"当你有一份多步骤任务的规范或需求时使用，在接触代码之前"

### 完整流程步骤
1. **声明**："我正在使用 writing-plans 技能来创建实现计划。"
2. **范围检查** —— 如果规范涵盖多个独立的子系统，建议拆分为单独的计划（每个子系统一个）。每个计划应能独立产出可工作、可测试的软件。
3. **文件结构** —— 在定义任务之前，规划哪些文件将被创建/修改以及各自的职责。设计具有清晰边界和定义良好的接口的单元。偏好更小、更专注的文件。一起变化的文件应该放在一起。在现有代码库中，遵循已建立的模式。
4. **编写计划文档**，包含强制头部：
   - `# [功能名称] 实现计划`
   - `> **对代理工作者：** 必需的子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans`
   - 目标、架构（2-3 句话）、技术栈
5. **定义任务**，结构为：任务 N、文件（创建/修改/测试）、包含实际代码的步骤、精确命令、预期输出、提交步骤
6. **自审** —— 规范覆盖（能否为每个规范需求指出对应的任务？）、占位符扫描、类型一致性（各任务间的签名是否匹配？）
7. **执行交接** —— 提供两个选项：子代理驱动（推荐）或内联执行

### 小粒度任务划分
每个步骤是一个操作（2-5 分钟）：
- "编写失败的测试" -> 步骤
- "运行测试确认其失败" -> 步骤
- "实现最简代码使测试通过" -> 步骤
- "运行测试确认通过" -> 步骤
- "提交" -> 步骤

### HARD GATE 注解
- **无占位符规则**：每个步骤必须包含实际内容。禁止的模式：
  - "TBD"、"TODO"、"稍后实现"、"补充细节"
  - "添加适当的错误处理" / "添加验证" / "处理边界情况"
  - "为以上代码编写测试"（没有实际的测试代码）
  - "类似于任务 N"（重复代码——工程师可能不按顺序阅读任务）
  - 描述要做什么但不展示如何做的步骤
  - 引用未在任何任务中定义的类型/函数/方法
- **需要完整代码**：如果步骤修改代码，展示代码
- **需要精确命令**：附带预期输出
- **强制头部**：每个计划必须以代理工作者通知开头

### 输入/输出预期
- **输入：** 来自 brainstorming 的已验证规范/设计文档
- **输出：** 位于 `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md` 的实现计划，包含可操作的复选框任务

### 与其他技能的集成
- **被调用者：** `brainstorming`（强制终端状态）
- **调用（执行交接）：** `subagent-driven-development` 或 `executing-plans`
- **所需上下文：** 应在专门的工作树中运行

### 工具注入点
- Write 用于计划文件
- TodoWrite 用于任务追踪
- Skill 工具用于执行交接
- Git 用于提交（在执行期间，委托出去）

### 核心精神
**零上下文容忍的计划。**计划假设执行工程师对代码库零上下文且品味存疑。每个细节必须明确——完整代码、精确路径、精确命令、预期输出。"类似于任务 N"规则的存在是因为工程师可能不按顺序阅读任务。TDD 被内置于步骤模式中（编写失败测试、验证失败、实现、验证通过、提交）。文件结构映射步骤确保在编写任何代码之前就锁定分解决策。

## 4. writing-skills

### 全名
`writing-skills`

### 描述
"在创建新技能、编辑现有技能或在部署前验证技能是否能正常工作时使用"

### 完整流程步骤

**RED —— 编写失败测试（基线）：**
1. 创建压力场景（纪律型技能需要 3 种以上组合压力：时间、沉没成本、权威、疲惫）
2. 在无技能的情况下运行场景 —— 记录确切行为、合理化理由（逐字）、触发违规的压力
3. 识别失败中的模式

**GREEN —— 编写最简技能：**
1. 编写仅针对那些特定合理化理由的技能
2. 在带技能的情况下运行相同场景 —— 验证代理现在遵守规范

**REFACTOR —— 堵住漏洞：**
1. 从测试中识别新的合理化理由
2. 添加明确的对抗措施（针对纪律型技能）
3. 从所有测试迭代中构建合理化表格
4. 创建红旗标志列表
5. 重新测试直到坚不可摧

**部署检查清单（每个技能必需）：**
- 名称：仅限字母、数字、连字符（无括号/特殊字符）
- 包含 `name` 和 `description` 的 YAML 前置元数据（最多 1024 字符）
- 描述以"Use when..."开头，包含具体触发条件/症状（绝不总结工作流程）
- 以第三人称编写
- 全文包含关键词以便搜索（错误、症状、工具）
- 清晰的概述，包含核心原则
- 针对在 RED 阶段确定的特定基线失败
- 一个优秀的示例（不是多语言）
- 仅当决策不明显时才包含小型流程图
- 快速参考表
- 常见错误章节
- 不采用叙事式讲故事
- 仅用于工具或繁重参考的支持文件
- 将技能提交到 git 并推送
- 在进入下一个技能之前停止 —— 不要批量处理技能而不逐个测试

### HARD GATE 注解
- **铁律**：没有失败的测试，就没有技能。适用于新技能**和**对现有技能的编辑。
- 先写技能再测试？删除它。重新开始。编辑技能不测试？同样的违规。
- **没有例外**：不适用于"简单的补充"、"只是加个章节"、"文档更新"
- 不要保留未经测试的更改作为"参考"——不要在运行测试时"改编"——删除就是删除
- **必需的背景知识**：使用此技能前必须理解 `superpowers:test-driven-development`
- 不要批量创建多个技能而不逐个测试

- 在当前技能验证完成之前不要进入下一个技能
- 不要因为"批量更高效"而跳过测试
- **违反规则的文字就是违反规则的精神**

### Claude 搜索优化（CSO）——关键章节
- **描述 = 何时使用，而非技能做什么**：测试发现，当描述总结工作流程时，Claude 可能会按照描述行事，而不是阅读完整的技能内容。一个描述说"任务间的代码审查"导致 Claude 只做了一次审查，尽管技能的流程图清楚地显示了两轮审查（先规范合规性，再代码质量）。
- 使用具体的触发条件、症状和表明此技能适用的情况
- 描述*问题*而非*特定语言的症状*
- 保持触发条件与技术无关，除非技能本身是特定于技术的
- 关键词：错误消息、症状、同义词、工具
- 以你*做什么*或核心洞察来命名：`condition-based-waiting` 优于 `async-test-helpers`
- 动名词 (-ing) 对流程类命名效果良好：`creating-skills`、`testing-skills`
- 使用 `**必需的子技能：** 使用 superpowers:name` 交叉引用其他技能——绝不使用 @ 语法（会强制加载并消耗上下文）

### Token 效率（关键）
- 入门工作流程：每个 <150 词
- 频繁加载的技能：总计 <200 词
- 其他技能：<500 词（保持简洁）
- 将细节移至工具帮助（--help），使用交叉引用，压缩示例，消除冗余

### 测试所有技能类型
- **纪律强化型技能**（TDD、verification-before-completion）：使用学术问题 + 压力场景 + 多种压力组合进行测试。成功标准：代理在最大压力下仍遵守规则。
- **技术型技能**（操作指南）：使用应用场景 + 变体场景 + 缺失信息测试进行测试。成功标准：代理正确应用技术。
- **模式型技能**（心智模型）：使用识别场景 + 应用场景 + 反例进行测试。成功标准：代理识别何时/如何应用模式。
- **参考型技能**（文档/API）：使用检索场景 + 应用场景 + 空白测试进行测试。成功标准：代理找到并应用参考信息。

### 防范技能被合理化的加固措施
- 明确堵住每一个漏洞——禁止特定的变通方法
- 处理"精神 vs 文字"的争论："违反规则的文字就是违反规则的精神"
- 从基线测试中构建合理化表格
- 创建用于自我检查的红旗标志列表
- 更新 CSO 以涵盖违规症状

### 输入/输出预期
- **输入：** 识别出的技能需求（重复出现的模式、不直观的技术）
- **输出：** 经过测试、部署的 SKILL.md，包含已验证的 RED（基线失败）、GREEN（通过测试）、REFACTOR（漏洞已堵住）

### 与其他技能的集成
- **必需的背景知识：** `test-driven-development`（基础前提条件）
- **测试方法论：** `@testing-skills-with-subagents.md`（压力场景、堵漏洞、元测试）
- **可选：** `anthropic-best-practices.md`（Anthropic 官方指南）
- **流程图渲染：** `render-graphs.js`（在技能目录中）

### 工具注入点
- 子代理分发（用于压力场景测试）
- TodoWrite（用于创建过程中的检查清单追踪）
- Read/Write 用于 SKILL.md 和支持文件
- Git 用于提交
- Graphviz DOT 渲染（用于流程图）
- `wc -w` 用于 token 效率验证

### 核心精神
**创建技能就是针对流程文档的 TDD。**相同的铁律，相同的 RED-GREEN-REFACTOR 循环。根本洞察：未经测试的技能总有漏洞——永远如此。15 分钟的测试可以节省数小时的调试时间。该技能具有深刻的元特性——它通过包含合理化表格、红旗标志列表、明确的漏洞封堵和 CSO 优化来展示自身的原则。关于描述字段的 CSO 发现尤为精妙：总结工作流程的描述创建了一个 Claude 会走的捷径，从而完全绕过技能主体。

## 5. subagent-driven-development

### 全名
`subagent-driven-development`

### 描述
"在当前会话中执行具有独立任务的实现计划时使用"

### 完整流程步骤

1. **读取计划文件一次** —— 提取所有任务的完整文本和上下文。记下上下文。创建包含所有任务的 TodoWrite。
2. **逐任务循环：**
   a. **调度实现者子代理**（使用 implementer-prompt.md），附带完整的任务文本 + 上下文 + 场景设定上下文
   b. **处理实现者状态**：
      - DONE -> 进入规范审查
      - DONE_WITH_CONCERNS -> 阅读关注点，如果涉及正确性/范围则处理，记录观察结果后继续
      - NEEDS_CONTEXT -> 提供缺失的上下文，重新调度
      - BLOCKED -> 评估：上下文问题（提供更多上下文后重新调度）？需要更强大的模型（重新调度）？任务太大（拆分为更小的部分）？计划有误（上报给人类）？
   c. **调度规范合规审查子代理**（spec-reviewer-prompt.md）—— 确认代码与规范匹配
   d. 如果发现规范问题：实现者（同一个子代理）修复，审查者再次审查。重复直到批准。
   e. **调度代码质量审查子代理**（code-quality-reviewer-prompt.md）—— 评估代码质量
   f. 如果发现质量问题：实现者（同一个子代理）修复，审查者再次审查。重复直到批准。
   g. 在 TodoWrite 中标记任务完成
   h. 还有更多任务？-> 循环到步骤 2a
3. **所有任务完成后：** 调度最终的代码审查子代理进行整体实现审查
4. **过渡**到 `superpowers:finishing-a-development-branch`

### 模型选择策略
- **机械任务**（独立函数、清晰规范、1-2 个文件）：快速/廉价模型
- **集成任务**（多文件协调、模式匹配、调试）：标准模型
- **架构/设计/审查任务**：最强模型
- **任务复杂度信号**：涉及 1-2 个文件且有完整规范 -> 廉价模型；涉及多个文件且需要集成 -> 标准模型；需要设计判断或广泛的代码库理解 -> 最强模型

### HARD GATE 注解
- **两阶段审查是强制性的**：先规范合规性审查，再代码质量审查。顺序错误 = 红旗标志。
- **绝不**跳过审查（规范合规性或代码质量）
- **绝不**带着未修复的问题继续
- **绝不**并行调度多个实现子代理（会冲突）
- **绝不**让子代理读取计划文件（改为提供完整文本——控制器提取并提供）
- **绝不**跳过场景设定上下文（子代理需要理解任务在整体中的位置）
- **绝不**忽略子代理的问题（先回答再让他们继续）
- **绝不**接受"差不多"的规范合规性（审查者发现了问题 = 未完成）
- **绝不**跳过审查循环（审查者发现问题 = 实现者修复 = 再次审查）
- **绝不**让实现者自行审查来代替正式审查（两者都需要）
- **绝不**在任一审查仍有未解决的问题时进入下一个任务
- **绝不**在未经用户明确同意的情况下在 main/master 分支上开始实现
- 如果实现者报告 BLOCKED 且计划有误 -> 上报给人类。**绝不**强制同一模型在没有修改的情况下重试。

### 输入/输出预期
- **输入：** 带有复选框任务的实现计划（来自 writing-plans）
- **输出：** 已实现、已测试、已审查的代码；过渡到 finishing-a-development-branch

### 与其他技能的集成
- **必需的子技能：** `using-git-worktrees`（隔离工作空间）、`writing-plans`（创建计划）、`requesting-code-review`（审查模板）、`finishing-a-development-branch`（完成）
- **子代理使用：** `test-driven-development`（每个任务的 TDD）
- **替代工作流程：** `executing-plans`（并行会话，无子代理支持）

### 工具注入点
- 子代理调度（实现者、规范审查者、代码质量审查者、最终审查者）
- 提示模板：`implementer-prompt.md`、`spec-reviewer-prompt.md`、`code-quality-reviewer-prompt.md`
- TodoWrite 用于任务追踪
- Read 用于计划文件（一次，由控制器执行）
- Skill 工具（调用 finishing-a-development-branch）
- Git 用于逐任务提交

### 核心精神
**每个任务的新曲子代理 + 两阶段审查 = 高质量、快速迭代。**关键洞察是上下文隔离：子代理绝不应继承你会话的历史——你精确构造它们需要的内容。这保留了你自己用于协调工作的上下文。控制器策划所需的确切上下文；子代理一次性获得完整信息。两阶段审查（先规范再质量）防止过度或不足构建，并确保实现质量良好。实现者的自行审查明确不能替代正式的审查阶段。成本模型是明确的：更多的子代理调用，但能及早发现问题（比以后调试更便宜）。

## 6. executing-plans

### 全名
`executing-plans`

### 描述
"当你有书面的实现计划需要在单独的会话中执行并附带审查检查点时使用"

### 完整流程步骤

**步骤 1：加载并审查计划**
1. 读取计划文件
2. 批判性地审查——识别对计划的问题或疑虑
3. 如果有疑虑：在开始前向人类伙伴提出
4. 如果没有疑虑：创建 TodoWrite 并继续

**步骤 2：执行任务**
对于每个任务：
1. 标记为 in_progress
2. 精确遵循每个步骤（计划有细粒度的步骤）
3. 按指定运行验证
4. 标记为已完成

**步骤 3：完成开发**
在所有任务完成并验证后：
- 声明："我正在使用 finishing-a-development-branch 技能来完成这项工作。"
- **必需的子技能：** 使用 superpowers:finishing-a-development-branch
- 遵循该技能：验证测试、呈现选项、执行选择

### HARD GATE 注解
- **立即停止执行当**：遇到阻塞、计划有阻止开始的重大缺陷、指令不明确、验证反复失败
- **绝不**在未经用户明确同意的情况下在 main/master 分支上开始实现
- **绝不**强行突破阻塞——停下来询问
- **始终**先批判性地审查计划
- **始终**精确遵循计划步骤
- **始终**按指定运行验证

### 输入/输出预期
- **输入：** 书面的实现计划（来自 writing-plans）
- **输出：** 已实现的代码；过渡到 finishing-a-development-branch

### 与其他技能的集成
- **必需的工作流技能：** `using-git-worktrees`（隔离工作空间）、`writing-plans`（创建计划）、`finishing-a-development-branch`（完成）
- **备注：** 明确告知用户在子代理可用时，subagent-driven-development 更优
- **被调用者：** writing-plans 作为内联执行选项

### 工具注入点
- TodoWrite 用于任务追踪
- Read 用于计划文件
- Skill 工具用于 finishing-a-development-branch
- Git 用于提交
- 测试运行器用于验证

### 核心精神
**忠于计划的执行，辅以批判性审查。**加载计划，在开始前批判性地审查，然后精确遵循步骤。该技能承认自身的局限性——它明确推荐 subagent-driven-development 作为更优的替代方案。它的价值在于并行会话场景，在该场景中你将计划交给一个带有全新上下文的独立代理实例。"不要强行突破阻塞——停下来询问"是首要规则。这是实现技能中最简单的一个，是有意为之——它专为没有子代理支持的环境设计。

## 7. test-driven-development

### 全名
`test-driven-development`

### 描述
"在实现任何功能或错误修复时、在编写实现代码之前使用"

### 完整流程步骤

**RED —— 编写失败测试：**
- 编写一个最简测试，展示应该发生什么
- 要求：一个行为、清晰的名称、真实代码（除非不可避免，否则不使用 mock）
- 示例：好（清晰名称：'失败操作重试 3 次'、测试真实行为、一件事）；差（模糊名称：'重试工作'、测试 mock 而非代码）

**验证 RED —— 看它失败（强制）：**
- 运行测试命令
- 确认：测试失败（而非报错）、失败消息符合预期、因缺少功能而失败（而非拼写错误）
- 测试通过了？你在测试已有行为。修复测试。
- 测试报错了？修复错误，重新运行直到正确失败。

**GREEN —— 最简代码：**
- 编写能让测试通过的最简单代码
- 不要添加功能、不要重构其他代码、不要"改进"超出测试的范围
- 示例：好（刚好足以通过）；差（过度工程化，违反 YAGNI）

**验证 GREEN —— 看它通过（强制）：**
- 运行测试命令
- 确认：测试通过、其他测试仍然通过、输出干净（无错误、无警告）
- 测试失败？修复代码，而非测试。
- 其他测试失败？立即修复。

**REFACTOR —— 清理：**
- 仅在通过绿色后：消除重复、改进命名、提取辅助方法
- 保持测试通过。不要添加行为。

**重复** —— 下一个功能的失败测试。

### HARD GATE 注解
- **铁律**：没有失败的测试在先，就没有生产代码
- 先写了代码再写测试？删除它。重新开始。
- **没有例外**：不要保留作为"参考"，不要在写测试时"改编"它，不要看它。删除就是删除。
- 验证 RED（看它失败）是强制性的。绝不跳过。
- 验证 GREEN（看它通过）是强制性的。绝不跳过。
- **违反规则的文字就是违反规则的精神。**
- 在想"就这一次跳过 TDD"？停下来。那是在合理化。

### 合理化预防（揭穿 16 个借口）
| 借口 | 现实 |
|---|---|
| "太简单了不用测试" | 简单代码也会坏。测试只需 30 秒。 |
| "我之后会测试" | 测试立即通过什么都证明不了。 |
| "事后测试能达到同样目的" | 事后测试 = "这是干什么的？" 测试优先 = "这应该干什么？" |
| "已经手动测试过了" | 临时测试 != 系统测试。没有记录，无法重新运行。 |
| "删除 X 小时的工作太浪费了" | 沉没成本谬误。保留未经验证的代码就是技术债务。 |
| "保留作为参考，先写测试" | 你会改编它。那还是事后测试。删除就是删除。 |
| "需要先探索" | 可以。扔掉探索代码，用 TDD 重新开始。 |
| "难测试 = 设计不清晰" | 倾听测试的声音。难测试 = 难使用。 |
| "TDD 会拖慢我" | TDD 比调试更快。务实的做法 = 测试优先。 |
| "手动测试更快" | 手动无法证明边界情况。你每次修改都得重新测试。 |
| "现有代码没有测试" | 你正在改进它。为现有代码添加测试。 |
| （以及技能中合理化表格里的另外 5 个） |

### 红旗标志 —— 停下来重新开始
- 代码先于测试、测试在实现之后编写、测试立即通过、无法解释测试为何失败
- 测试"稍后"添加、合理化"就这一次"
- "事后测试能达到同样目的"、"这是关于精神而非仪式"
- "保留作为参考"、"已经花了 X 小时，删除太浪费了"
- 所有这些都意味着：删除代码。用 TDD 重新开始。

### 验证检查清单
- [ ] 每个新函数/方法都有测试
- [ ] 在实现前观察了每个测试失败
- [ ] 每个测试因预期原因失败（缺少功能，而非拼写错误）
- [ ] 编写了最简代码来通过每个测试
- [ ] 所有测试通过
- [ ] 输出干净（无错误、警告）
- [ ] 测试使用真实代码（仅当不可避免时才用 mock）
- [ ] 覆盖了边界情况和错误

不能勾选所有项？你跳过了 TDD。重新开始。

### 输入/输出预期
- **输入：** 功能需求或待修复的错误
- **输出：** 经过测试的代码，带有先失败后通过的测试循环；失败测试作为回归防护留存

### 与其他技能的集成
- **被调用者：** `systematic-debugging`（阶段 4，步骤 1 —— 创建失败测试）、`writing-skills`（必需的背景知识）
- **被调用者：** `subagent-driven-development`（子代理使用 TDD）
- **被调用者：** `verification-before-completion`（验证修复有效）
- **测试反模式：** `@testing-anti-patterns.md`（避免 mock 陷阱）

### 工具注入点
- Bash/PowerShell 用于测试命令
- Read 用于现有代码
- Write 用于测试文件和生产代码
- Git 用于提交

### 核心精神
**如果你没有看到测试失败，你就不知道它是否测试了正确的东西。**实现之后编写的测试会立即通过，这什么都证明不了——它们可能测试了错误的东西、测试了实现而非行为、或者遗漏了你忘记的边界情况。测试优先迫使你看到测试失败，证明它确实在测试某些东西。沉没成本谬误被正面处理：时间已经花掉了；你的选择是在 TDD 下重写（高置信度）或保留未经验证的代码（技术债务）。该技能还充当设计质量指标："难测试 = 难使用。"不 mock 原则强制依赖注入和清晰的接口。

## 8. dispatching-parallel-agents

### 全名
`dispatching-parallel-agents`

### 描述
"当面对 2 个以上可以在没有共享状态或顺序依赖的情况下独立完成的任务时使用"

### 完整流程步骤
1. **识别独立领域** —— 按问题出在哪里对失败/任务进行分组。每个领域是独立的（修复一个不影响其他）。
2. **创建聚焦的代理任务** —— 每个代理获得：特定范围（一个测试文件或子系统）、明确的目标（使这些测试通过）、约束条件（不要改动其他代码）、预期输出（你发现和修复了什么的小结）。
3. **并行调度** —— 每个问题领域一个代理，全部并发运行。
4. **审查并集成** —— 阅读每个小结，验证修复不冲突，运行完整测试套件，集成所有更改。

### 代理提示结构
好的代理提示：
1. **聚焦的** —— 一个清晰的问题领域
2. **自包含的** —— 理解问题所需的所有上下文
3. **对输出有具体要求** —— 代理应该返回什么？

### HARD GATE 注解
- **不要使用当**：失败是相关的（修复一个可能修复其他）、需要理解完整系统状态、代理会相互干扰（编辑相同文件、使用相同资源）、探索性调试（还不知道哪里坏了）
- **绝不**让提示过于宽泛（"修复所有测试"）—— 代理会迷失
- **绝不**不提供上下文或模糊的输出预期
- **绝不**不设约束条件就调度 —— 代理可能重构一切

### 输入/输出预期
- **输入：** 多个独立的问题领域（测试失败、带有错误消息的损坏子系统）
- **输出：** 每个代理返回根因和更改的小结；集成的最终状态，完整测试套件通过

### 与其他技能的集成
- **与以下对比：** `subagent-driven-development`（明确禁止并行实现子代理以避免冲突）
- **在以下之前调用：** 验证步骤（审查并集成）
- **可由以下调用：** 任何有独立失败需要调查的上下文

### 工具注入点
- 子代理/任务调度机制（并行调用）
- 测试套件运行器（最终集成验证）

### 核心精神
**独立问题的并行调查。**当你有多个不相关的失败时，顺序调查是在浪费时间。关键洞察是严格的独立性检查：如果失败是相关的或共享状态，不要并行化。真实世界的例子展示了 6 个跨 3 个文件的失败通过并行调度 3 个代理在原本处理 1 个文件的时间内解决。每个代理的范围很窄（一个测试文件），目标清晰，输出预期明确。这明确不是用于并行实现（subagent-driven-development 禁止此事）——而是用于并行调查。

## 9. systematic-debugging

### 全名
`systematic-debugging`

### 描述
"在遇到任何错误、测试失败或意外行为时使用，在提出修复方案之前"

### 完整流程步骤

**阶段 1：根因调查（在尝试任何修复之前）：**
1. 仔细阅读错误消息 —— 完整读取堆栈跟踪，记下行号/文件路径/错误码
2. 稳定复现 —— 精确步骤，每次都可靠？如果无法复现，收集更多数据，不要猜测
3. 检查最近的更改 —— git diff、最近的提交、新的依赖、配置更改、环境差异
4. 在多组件系统中收集证据 —— 在每个组件边界添加诊断仪表。记录进入什么、离开什么。验证环境/配置传播。检查每层的状态。运行一次收集证据，显示**在哪里**中断，然后分析证据以识别出故障组件，然后调查该特定组件。
5. 追踪数据流 —— 通过调用栈向后追踪。坏值从哪里来？是谁用这个坏值调用的？继续向上追踪直到找到源头。在源头修复，而非在症状处。

**阶段 2：模式分析：**
1. 在同一个代码库中找到工作正常的示例
2. 对照参考进行比较 —— 完整阅读参考实现，不要略读，在应用之前完全理解模式
3. 识别工作与不工作版本之间的差异 —— 列出每一个差异，无论多小，不要假设"这不重要"
4. 理解依赖关系 —— 涉及哪些其他组件、设置、配置、环境、假设？

**阶段 3：假设与测试（科学方法）：**
1. 形成单一假设 —— 清晰陈述"我认为 X 是根因，因为 Y"，要具体不要模糊
2. 最小化测试 —— 尽可能小的改动，一次只变一个变量，不要同时修复多个问题
3. 在继续之前验证 —— 有效？阶段 4。无效？形成**新的**假设。不要再叠加更多修复。
4. 当你不知道时 —— 说"我不理解 X"，不要假装知道，寻求帮助，进一步研究

**阶段 4：实现：**
1. 创建失败测试用例 —— 最简单的可复现方式，尽可能自动化，修复前**必须**有
2. 实施单一修复 —— 解决识别出的根因，一次**一个**更改，没有"既然来了就顺便改进一下"，没有捆绑的重构
3. 验证修复 —— 测试现在通过了？没有其他测试被破坏？问题确实解决了？
4. 如果修复不起作用 —— 停。计数：尝试了多少次修复？如果 < 3：返回阶段 1。如果 >= 3：停下来质疑架构。在没有架构讨论的情况下**不要**尝试第 4 次修复。
5. **如果 3 次以上修复失败：质疑架构** —— 表明架构问题的模式：每次修复揭示新的共享状态/耦合、修复需要"大规模重构"、每次修复在其他地方创建新症状。停下来质疑基础。与人类伙伴讨论。

### HARD GATE 注解
- **铁律**：没有根因调查在先，就没有修复
- 如果你没有完成阶段 1，就不能提出修复方案
- 你**必须**完成每个阶段才能进入下一个
- **违反此流程的文字就是违反调试的精神**
- 如果 3 次以上修复失败：架构问题。不是假设失败——是架构错误。
- 95% 的"找不到根因"案例都是调查不完整
- 16 个红旗模式意味着停止（包括："先快速修复，以后再调查"、"试试改 X 看看是否有效"、"再试一次修复"、在追踪数据流之前提出解决方案等）

### 输入/输出预期
- **输入：** 错误、测试失败、意外行为（附带错误消息或症状）
- **输出：** 根因已识别、修复已实施（一个更改）、为回归创建了失败测试、架构问题已浮出水面（如果 3 次以上修复失败）

### 与其他技能的集成
- **使用：** `test-driven-development`（阶段 4，步骤 1 —— 创建失败测试用例）
- **使用：** `verification-before-completion`（在声称成功之前验证修复有效）
- **目录中的支持技术：** `root-cause-tracing.md`（向后追踪）、`defense-in-depth.md`（多层验证）、`condition-based-waiting.md`（用轮询替代超时）

### 工具注入点
- Bash/PowerShell 用于诊断命令（在组件边界添加 echo 仪表）
- Read 用于错误消息、日志、代码、堆栈跟踪
- Git（diff、log 用于最近更改）
- Skill 工具（调用 test-driven-development 进行回归测试）
- 测试运行器

### 核心精神
**要么找到根因，要么什么都不做。**随机修复浪费时间并引入新错误。快速补丁掩盖了根本问题。四个阶段是将科学方法应用于调试：收集证据（阶段 1）、找到模式（阶段 2）、形成假设（阶段 3）、在源头修复（阶段 4）。3 次修复规则尤为重要——在 3 次修复尝试失败后，问题很可能是架构性的，而非简单错误，不质疑基础的话再多的"修复"也解决不了。多组件证据收集模式尤为突出：仪表化每个边界，运行一次看看**在哪里**中断，**然后**调查该组件。这防止了在错误层进行猜测。

## 10. requesting-code-review

### 全名
`requesting-code-review`

### 描述
"在完成任务、实现主要功能、或在合并之前用于验证工作是否符合需求时使用"

### 完整流程步骤
1. **获取 git SHA**：`BASE_SHA=$(git rev-parse HEAD~1)`（或 origin/main）和 `HEAD_SHA=$(git rev-parse HEAD)`
2. **调度代码审查子代理**，使用 `code-reviewer.md` 中的模板，填充占位符：
   - `{WHAT_WAS_IMPLEMENTED}` —— 你刚刚构建了什么
   - `{PLAN_OR_REQUIREMENTS}` —— 它应该做什么
   - `{BASE_SHA}` —— 起始提交
   - `{HEAD_SHA}` —— 结束提交
   - `{DESCRIPTION}` —— 简要总结
3. **处理反馈**：
   - 立即修复关键问题
   - 在继续之前修复重要问题
   - 记录次要问题以备后续
   - 如果审查者错了则反驳（附上推理）

### HARD GATE 注解
- **绝不**因为"这很简单"就跳过审查
- **绝不**忽略关键问题
- **绝不**带着未修复的重要问题继续
- **绝不**与有效的技术反馈争论
- 如果审查者错了：用技术推理反驳，展示证明其有效的代码/测试，请求澄清

### 输入/输出预期
- **输入：** Git SHA（之前/之后）、对所实现内容的描述、计划/需求文档
- **输出：** 审查反馈，包含优势、问题（按严重性标记：关键/重要/次要）、评估

### 与其他技能的集成
- **被以下使用：** `subagent-driven-development`（在**每个**任务之后——在问题级联之前捕获）
- **被以下使用：** `executing-plans`（每批 3 个任务之后）
- **在以下场景中使用：** 临时开发（合并前、卡住时）
- **使用模板：** `requesting-code-review/code-reviewer.md`
- **与以下配对：** `receiving-code-review`（用于评估和处理反馈）

### 工具注入点
- 子代理调度（代码审查者类型）
- Bash 用于 `git rev-parse`
- gh API（用于与 PR 相关的审查）

### 核心精神
**尽早审查，经常审查。**调度代码审查子代理以在问题级联之前捕获它们。审查者获得精心构造的评估上下文——绝无你会话的历史。这使审查者专注于工作产品而非你的思考过程，并保留你自己的上下文以继续工作。反馈按严重性分类（关键、重要、次要），每级都有明确的行动要求。

## 11. receiving-code-review

### 全名
`receiving-code-review`

### 描述
"在收到代码审查反馈时使用，在实施建议之前，特别是当反馈看起来不明确或技术上可疑时——需要技术严谨性和验证，而非表演性的同意或盲目实施"

### 完整流程步骤
1. **阅读** —— 完整阅读反馈，不要做出反应
2. **理解** —— 用自己的话重述要求（或提问）
3. **验证** —— 对照代码库现实进行检查
4. **评估** —— 对这个代码库来说技术上合理吗？
5. **回应** —— 技术性确认或有理有据的反驳
6. **实施** —— 一次一个项目，每个都测试

### 禁止的回应
- **绝不**："你说得太对了！"、"好观点！"、"极好的反馈！"、"我现在就来实施"（在验证之前）
- **取而代之**：重述技术需求、提出澄清性问题、用技术推理进行反驳、直接开始工作（行动胜于言语）
- **绝不**表达感激："感谢 [任何东西]" 被明确禁止。"为什么不说谢谢：行动胜于言语。直接修复就好。代码本身会证明你听到了反馈。"

### 处理不清晰的反馈
- 如果有任何项目不明确：停 —— 在澄清之前不要实施任何内容
- 为什么：项目可能是相关的。部分理解 = 错误的实现。

### 按来源处理
- **来自人类伙伴**：值得信赖 —— 在理解后实施。如果范围不明确仍然要问。不要表演性同意。直接行动或技术确认。
- **来自外部审查者**：检查：对这个代码库来说技术上正确吗？是否会破坏现有功能？当前实现的原因？在所有平台上都能工作吗？审查者理解完整上下文吗？如果建议看起来不对，用技术推理反驳。

### YAGNI 检查
如果审查者建议"正确实施"，用 grep 搜索代码库以查看实际使用情况。如果未使用："这个端点没有被调用。删除它（YAGNI）？"如果被使用则正确实施。规则："你和我都向同一个人汇报。如果我们不需要这个功能，就不要添加它。"

### 多项目反馈的实施顺序
1. 首先**澄清**一切不明确的内容
2. 阻塞性问题（破坏性、安全性）
3. 简单修复（拼写错误、导入）
4. 复杂修复（重构、逻辑）
5. 单独测试每个修复
6. 验证没有回归

### 何时反驳
建议破坏现有功能、审查者缺乏完整上下文、违反 YAGNI、对此技术栈来说技术上不正确、遗留/兼容性原因、与人类伙伴的架构决策冲突。使用技术推理，而非防御性。

### 优雅地纠正反驳
如果你反驳了但错了："你是对的 —— 我检查了 [X]，它确实 [Y]。正在实施。"不用长道歉、不用为你为什么反驳辩护、不过度解释。

### HARD GATE 注解
- **绝不**表演性同意（明确违反 CLAUDE.md）
- **绝不**盲目实施 —— 先在代码库中验证
- **绝不**在未单独测试每个修复的情况下批量处理
- **绝不**假设审查者是对的 —— 检查它是否会破坏东西
- **绝不**避免反驳 —— 技术正确性优先于社交舒适
- **绝不**部分实施 —— 先澄清所有项目
- **绝不**不经验证就继续 —— 陈述限制，请求指示

### 输入/输出预期
- **输入：** 代码审查反馈（来自人类伙伴或外部审查者）
- **输出：** 已验证的实施，针对达成一致的反馈项目；针对不同意的项目进行有理有据的反驳

### 与其他技能的集成
- **在以下之后使用：** `requesting-code-review` 提供反馈
- **与以下配对：** `requesting-code-review`（同一枚代码审查硬币的两面）
- **GitHub 集成：** 回复 GitHub 上的内联审查评论作为评论回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而非作为 PR 顶层评论

### 工具注入点
- Grep（用于 YAGNI 检查 —— grep 代码库查找实际使用情况）
- Read（用于代码库验证）
- gh api（用于 GitHub 评论回复）

### 核心精神
**技术正确性优先于社交舒适。**代码审查需要技术评估，而非情感表演。这是整个系统中反表演性最强的技能。"谢谢"被明确禁止——行动胜于言语，直接修复就好。外部反馈 = 需要评估的建议，而非需要服从的命令。YAGNI 检查尤为犀利：来自审查者的"正确实施"会在实施之前触发对实际使用情况的 grep。如果该功能未被使用，反驳以删除而非"正确实施"。该技能还提供了一个安全词（"Strange things are afoot at the Circle K"）用于代理在社交上对反驳感到不适的情况。

## 12. using-git-worktrees

### 全名
`using-git-worktrees`

### 描述
"在开始需要与当前工作空间隔离的功能工作之前，或在执行实现计划之前使用——创建隔离的 git 工作树，带有智能目录选择和安全验证"

### 完整流程步骤

**1. 目录选择（优先级顺序）：**
- 检查已存在的：`.worktrees/`（首选，隐藏）或 `worktrees/`（替代）。如果两者都存在，`.worktrees/` 胜出。
- 检查 CLAUDE.md 中的工作树目录偏好
- 如果都不存在且没有 CLAUDE.md 偏好：向用户询问两个选项：
  1. `.worktrees/`（项目本地，隐藏）
  2. `~/.config/superpowers/worktrees/<项目名称>/`（全局位置）

**2. 安全验证：**
- 对于项目本地目录：必须通过 `git check-ignore -q .worktrees` 验证目录已被忽略
- 如果未被忽略：向 .gitignore 添加适当行，提交更改（根据"立即修复损坏的东西"原则），然后继续
- 对于全局目录：无需 .gitignore 验证（完全在项目外）

**3. 创建步骤：**
1. 检测项目名称：`project=$(basename "$(git rev-parse --show-toplevel)")`
2. 创建工作树：`git worktree add <path> -b <BRANCH_NAME>`
3. cd 到该路径
4. 运行项目设置（自动检测）：

### 设置自动检测
| 找到的文件 | 命令 |
|---|---|
| package.json | npm install |
| Cargo.toml | cargo build |
| requirements.txt | pip install -r requirements.txt |
| pyproject.toml | poetry install |
| go.mod | go mod download |

**4. 验证干净的基线：** 运行适合项目的测试命令
- 如果测试失败：报告失败，询问是继续还是调查
- 如果测试通过：报告就绪

**5. 报告位置：** "工作树已就绪，位于 <完整路径>。测试通过（<N> 个测试，0 个失败）。已准备好实现 <功能名称>。"

### HARD GATE 注解
- **绝不**不经验证目录被忽略就创建工作树（项目本地）
- **绝不**跳过基线测试验证
- **绝不**在测试失败的情况下不经询问就继续
- **绝不**在模棱两可的情况下假设目录位置
- **绝不**跳过 CLAUDE.md 检查
- **始终**遵循目录优先级：已存在 > CLAUDE.md > 询问
- **始终**验证项目本地目录已被忽略
- **始终**自动检测并运行项目设置
- **始终**验证干净的测试基线

### 输入/输出预期
- **输入：** 功能/分支名称、项目路径
- **输出：** 在确定路径上的隔离工作树，带有干净的测试基线

### 与其他技能的集成
- **被调用者：** `brainstorming`（当设计获批准且实现跟进时）、`subagent-driven-development`（执行任务前必需）、`executing-plans`（执行任务前必需）
- **与以下配对：** `finishing-a-development-branch`（工作完成后清理必需）

### 工具注入点
- Bash 用于 git 命令（`git worktree add`、`git check-ignore`、`git rev-parse`）
- Bash 用于项目设置命令（npm、cargo、pip、poetry、go）
- Read 用于 CLAUDE.md
- Write 用于 .gitignore（如果需要）
- 测试套件运行器

### 核心精神
**系统的目录选择 + 安全验证 = 可靠的隔离。**优先级链（已存在目录 > CLAUDE.md > 询问用户）在大多数情况下无需用户输入即可消除歧义。忽略验证防止了将工作树内容提交到仓库的灾难性错误。干净的基线验证确保预先存在的测试失败不会与新错误混淆。工作树不仅被创建——在工作开始前被设置并验证。

## 13. finishing-a-development-branch

### 全名
`finishing-a-development-branch`

### 描述
"在实现完成、所有测试通过、需要决定如何集成工作时使用——通过呈现结构化选项（合并、PR 或清理）来指导开发工作的完成"

### 完整流程步骤

**步骤 1：验证测试**
运行项目的测试套件。如果测试失败：展示失败。停止。在测试通过之前无法继续。

**步骤 2：确定基础分支**
`git merge-base HEAD main` 或 `git merge-base HEAD master`。询问："此分支从 main 分离——是否正确？"

**步骤 3：呈现选项（恰好 4 个，简洁，不解释）**
1. 合并回 <base-branch> 本地
2. 推送并创建 Pull Request
3. 保持分支不变（我稍后处理）
4. 放弃此工作

**步骤 4：执行选择**

*选项 1 —— 本地合并：*
```bash
git checkout <base-branch>
git pull
git merge <feature-branch>
<test command>  # 验证合并结果的测试
git branch -d <feature-branch>
```
然后：清理工作树

*选项 2 —— 推送并创建 PR：*
```bash
git push -u origin <feature-branch>
gh pr create --title "<title>" --body "<summary + test plan>"
```
保留工作树（不要清理）

*选项 3 —— 保持原样：*
报告："保留分支 <name>。工作树保留在 <path>。"
不要清理工作树。

*选项 4 —— 放弃：*
先确认："这将永久删除：分支 <name>、所有提交：<list>、工作树在 <path>。输入 'discard' 以确认。"
```bash
git checkout <base-branch>
git branch -D <feature-branch>
```
然后：清理工作树

**步骤 5：清理工作树**
对于选项 1、2、4：检查是否在工作树中，然后 `git worktree remove <path>`。
对于选项 3：保留工作树。

### HARD GATE 注解
- **绝不**在测试失败的情况下继续
- **绝不**不经验证测试就合并
- **绝不**不经输入确认就删除工作
- **绝不**未经明确请求就强制推送
- **始终**在提供选项之前验证测试
- **始终**呈现恰好 4 个选项（不多不少，不解释）
- **始终**对选项 4 获取输入"discard"确认
- **始终**仅对选项 1 和 4 清理工作树（不适用于选项 2 或 3）

### 输入/输出预期
- **输入：** 已完成实现，测试通过；带有提交的功能分支
- **输出：** 执行所选完成操作（合并、创建 PR、保留或放弃）

### 与其他技能的集成
- **被调用者：** `subagent-driven-development`（步骤 7 —— 所有任务完成后）、`executing-plans`（步骤 5 —— 所有批次完成后）
- **与以下配对：** `using-git-worktrees`（清理由该技能创建的工作树）

### 快速参考
| 选项 | 合并 | 推送 | 保留工作树 | 清理分支 |
|---|---|---|---|---|
| 1. 本地合并 | 是 | - | - | 是 |
| 2. 创建 PR | - | 是 | 是 | - |
| 3. 保持原样 | - | - | 是 | - |
| 4. 放弃 | - | - | - | 是（强制） |

### 工具注入点
- Bash 用于测试命令（npm test、cargo test、pytest、go test）
- Git 命令：merge-base、checkout、pull、merge、branch -d/-D、push、worktree list/remove
- gh CLI 用于创建 PR
- 用户输入用于选项选择和输入的"discard"确认

### 核心精神
**始终先验证测试，然后呈现清晰、无歧义的选项。**四个选项是固定的、简洁的，不留误解空间。选项 4（放弃）有一个故意的摩擦步骤，需要输入"discard"确认以防止意外数据丢失。清理规则是精确的：工作树对选项 2（PR）和 3（保留）保留，因为分支仍然存在且工作可能继续；只有对选项 1（已合并，完成）和 4（已放弃，消失）才清理。

## 14. verification-before-completion

### 全名
`verification-before-completion`

### 描述
"在即将声称工作已完成、已修复、或通过时使用，在提交或创建 PR 之前——要求运行验证命令并在做出任何成功断言之前确认输出；证据始终先于断言"

### 完整流程步骤

**门控函数（5 步）：**
1. **识别** —— 什么命令能证明这个断言？
2. **运行** —— 执行**完整**命令（重新运行、完整执行）
3. **读取** —— 完整输出、检查退出码、计数失败
4. **验证** —— 输出是否确认了断言？
   - 如果否：陈述实际状态并附上证据
   - 如果是：陈述断言并附上证据
5. **只有在那之后** —— 才能做出断言

跳过任何步骤 = 说谎，而非验证。

### HARD GATE 注解
- **铁律**：没有新鲜的验证证据，就没有完成断言
- 如果你没有在此消息中运行过验证命令，就不能声称它通过
- 跳过任何步骤 = 说谎，而非验证
- **违反此规则的文字就是违反此规则的精神**
- **始终在以下之前**：任何形式的成功/完成断言、任何满意表达、任何关于工作状态的正面陈述、提交、创建 PR、任务完成、进入下一个任务、委托给代理
- **规则适用于**：精确措辞、意译、同义词、成功的暗示、任何暗示完成/正确性的沟通

### 常见失败表
| 断言 | 需要 | 不足够 |
|---|---|---|
| 测试通过 | 测试命令输出：0 个失败 | 之前的运行、"应该通过" |
| 代码检查干净 | 代码检查输出：0 个错误 | 部分检查、外推 |
| 构建成功 | 构建命令：exit 0 | 代码检查通过、日志看起来不错 |
| 错误已修复 | 测试原始症状：通过 | 代码已更改，假设已修复 |
| 回归测试有效 | 红绿循环已验证 | 测试通过一次 |
| 代理已完成 | VCS diff 显示更改 | 代理报告"成功" |
| 满足需求 | 逐行检查清单 | 测试通过 |

### 红旗标志 —— 停止
- 使用"应该"、"可能"、"似乎"
- 在验证之前表达满意（"太好了！"、"完美！"、"完成了！"）
- 即将提交/推送/创建 PR 但未验证
- 相信代理的成功报告
- 依赖部分验证
- 在想"就这一次"
- 累了想结束工作
- 任何暗示成功但未运行验证的措辞

### 合理化预防
| 借口 | 现实 |
|---|---|
| "现在应该能工作了" | 运行验证 |
| "我有信心" | 信心 != 证据 |
| "就这一次" | 没有例外 |
| "代码检查通过了" | 代码检查 != 编译器 |
| "代理说成功了" | 独立验证 |
| "我累了" | 疲惫 != 借口 |
| "部分检查就够了" | 部分证明不了任何事 |
| "换了说法所以规则不适用" | 精神优先于文字 |

### 关键模式
- **测试**：[运行测试命令] [看到：34/34 通过] "所有测试通过" —— 而非"现在应该通过了" / "看起来正确"
- **回归（TDD 红绿）**：编写 -> 运行（通过） -> 还原修复 -> 运行（必须失败） -> 恢复 -> 运行（通过）
- **构建**：[运行构建] [看到：exit 0] "构建通过" —— 代码检查不检查编译
- **需求**：重新阅读计划 -> 创建检查清单 -> 逐项验证 -> 报告差距或完成
- **代理委托**：代理报告成功 -> 检查 VCS diff -> 验证更改 -> 报告实际状态

### 输入/输出预期
- **输入：** 关于工作状态的断言（测试通过、错误已修复、代码检查干净、构建成功等）
- **输出：** 支持或反驳该断言的新鲜验证证据

### 与其他技能的集成
- **被以下使用：** 所有实现/调试技能 —— 通用的完成前门控
- **被以下使用：** `systematic-debugging`（在声称成功之前验证修复有效）
- **被以下使用：** `test-driven-development`（验证测试通过）
- **被以下使用：** `finishing-a-development-branch`（在合并前验证测试）
- **与以下配对：** 每个做出完成断言的技能

### 工具注入点
- Bash/PowerShell 用于验证命令（测试运行器、代码检查器、构建命令）
- Read 用于命令输出检查
- Git 操作用于 VCS diff/变更集
- 任何能证明断言的命令

### 核心精神
**证据始终先于断言。**不经验证就声称工作完成是不诚实，而非高效。该技能的存在是因为有 24 个有记录的失败记忆：信任被破坏、未定义的函数被发布、缺失的需求被发布、以及虚假完成 -> 重定向 -> 返工浪费时间。"常见失败"表对什么构成有效证据与什么是不充分的替代品格外精确。"代理已完成"需要显示更改的 VCS diff —— 而非代理的"成功"报告。"回归测试有效"需要完整的红绿循环 —— 而非测试仅通过一次。没有捷径，没有例外，没有"就这一次"。

## 跨领域主题

### 流程技能 vs. 实现技能
该系统清晰地分为两个层次：
- **流程/路由：** `using-superpowers`（入口点）、`brainstorming`（设计优先）、`writing-plans`（计划）
- **执行：** `subagent-driven-development`、`executing-plans`、`systematic-debugging`
- **质量：** `test-driven-development`、`verification-before-completion`、`requesting-code-review`、`receiving-code-review`
- **基础设施：** `using-git-worktrees`、`dispatching-parallel-agents`、`finishing-a-development-branch`
- **元：** `writing-skills`

### 三项基本原则（铁律）
1. **没有根因调查在先，就没有修复**（systematic-debugging）
2. **没有失败的测试在先，就没有生产代码**（test-driven-development）
3. **没有新鲜的验证证据，就没有完成断言**（verification-before-completion）
4. **没有失败的测试在先，就没有技能**（writing-skills）

### HARD-GATE 模式
多个技能使用明确的门控注解来阻止过早行动。这些注解被放置在关键的过渡点（实现之前、修复之前、完成断言之前）。它们与反合理化表格和红旗标志列表配对，列举哪些想法表明违规正在进行中。

### 反表演文化
`receiving-code-review` 是一个突出的例子：它明确禁止"你说得太对了！"、"好观点！"、"谢谢！"——要求技术评估而非社交舒适。这延伸到 `verification-before-completion` 禁止在证据之前表达满意。该系统重视技术诚实胜于礼貌。

### 工作树隔离架构
`using-git-worktrees` 为功能工作创建物理隔离。`subagent-driven-development` 增加了认知隔离（每个任务的新子代理，不继承上下文）。`finishing-a-development-branch` 确保清理。它们共同形成一个完整的隔离生命周期。

### 两阶段审查流水线
`subagent-driven-development` 建立了一个强制性的两阶段审查：
1. **先规范合规性** —— 代码是否符合要求？（防止过度/不足构建）
2. **再代码质量** —— 实现构建得好吗？（防止技术债务）
顺序至关重要，并作为红旗标志强制执行。

### "1% 概率"规则
`using-superpowers` 确立了即使只有 1% 的概率某个技能可能适用，也足以调用它。这与一个针对 12 种特定合理化理由的红旗表格相配套，以阻止跳过技能检查。

### 功能开发的技能链（完整流程）
1. `using-superpowers` -> 触发 `brainstorming`
2. `brainstorming` -> 设计文档 -> 触发 `writing-plans`
3. `writing-plans` -> 计划文件 -> 触发 `subagent-driven-development` 或 `executing-plans`
4. `subagent-driven-development` -> 每个任务：实现，然后 `requesting-code-review`
5. `finishing-a-development-branch` -> 所有任务完成后：验证、呈现选项、执行
6. `using-git-worktrees` -> 清理（如果使用了工作树）
